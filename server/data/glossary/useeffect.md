# useEffect — теория, практика и зачем это вообще нужно

Формат как в прошлых файлах: сначала понимание механики, потом руки — практика с разбором.

---

## 1. Зачем useEffect существует — проблема, которую он решает

React-компонент — это функция, которая возвращает JSX по текущим props/state. Но реальным приложениям нужно делать вещи **за пределами рендера**: сходить за данными на сервер, подписаться на событие, завести таймер, синхронизировать что-то с внешним миром (DOM API, localStorage, WebSocket). Это называется **side effect** (побочный эффект) — то, что не является чистым вычислением UI из данных.

**useEffect — это способ сказать React:** "после того как отрисуешь компонент на экране, выполни вот этот код, который взаимодействует с чем-то внешним". Без этого пришлось бы пытаться делать side-эффекты прямо в теле функции-компонента — а это ломает предсказуемость рендера (побочный эффект может сработать несколько раз при каждом ре-рендере без контроля).

В классовых компонентах (до хуков) для этого были отдельные методы жизненного цикла: `componentDidMount`, `componentDidUpdate`, `componentWillUnmount`. useEffect — это все три метода, объединённые в одну модель через понятие "зависимостей".

## 2. Механика: когда именно срабатывает эффект

**Ключевое правило:** useEffect выполняется **после** того, как React отрисовал изменения в DOM — не блокирует отображение на экране (в отличие от useLayoutEffect, о нём в конце).

```jsx
function Example() {
  console.log("1. Рендер компонента");
  useEffect(() => {
    console.log("2. Эффект выполнился после рендера");
  });
  return <div>Привет</div>;
}
```
Порядок в консоли всегда: сначала рендер, потом эффект — даже если эффект написан в середине функции.

### Массив зависимостей — три режима работы

```jsx
useEffect(() => { /* код */ });            // без массива — после КАЖДОГО рендера
useEffect(() => { /* код */ }, []);        // пустой массив — ТОЛЬКО один раз, после первого рендера (mount)
useEffect(() => { /* код */ }, [a, b]);    // с зависимостями — когда a или b изменились
```

**Почему это работает именно так:** React после каждого рендера сравнивает текущие значения зависимостей с теми, что были на предыдущем рендере (через `Object.is`, то же сравнение, что и `===`). Если хоть одно значение отличается — эффект запускается снова. Если зависимостей нет вообще (`[]`) — сравнивать нечего, значит "изменений" никогда не происходит после первого раза.

**Частая ловушка-вопрос на собесе:** "Что если забыть указать зависимость, которая используется внутри эффекта?" — эффект будет работать со **старым (устаревшим) значением** этой переменной — это называется **stale closure**. React в строгом режиме и ESLint-плагин `eslint-plugin-react-hooks` подсвечивают такие случаи именно поэтому.

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      console.log(count); // всегда будет печатать 0!
    }, 1000);
    return () => clearInterval(id);
  }, []); // count не в зависимостях — замыкание "заморозило" его на значении при монтировании

  return <button onClick={() => setCount(c => c + 1)}>+</button>;
}
```
Это классический вопрос "почему тут всегда 0" — ответ: замыкание внутри эффекта захватило `count` таким, каким он был на момент **первого** рендера (когда эффект создался с `[]`), и больше не обновляется, потому что эффект не перезапускается.

## 3. Cleanup-функция — зачем и когда вызывается

Если эффект что-то "включает" (подписка, таймер, слушатель события) — его нужно "выключить", когда компонент размонтируется или перед следующим запуском эффекта. Для этого эффект может **вернуть функцию** — это и есть cleanup.

```jsx
useEffect(() => {
  const handler = () => console.log(window.innerWidth);
  window.addEventListener("resize", handler);
  return () => window.removeEventListener("resize", handler); // cleanup
}, []);
```

**Когда именно вызывается cleanup:**
1. Перед тем как эффект запустится **повторно** (если зависимости изменились) — React сначала выполнит cleanup от предыдущего запуска, потом новый эффект.
2. При **размонтировании** компонента — финальный cleanup, чтобы не осталось "утечек" (висящих подписок, таймеров, слушателей).

**Почему это важно объяснить именно так на собесе:** без cleanup при каждом изменении зависимости добавлялся бы новый слушатель события без удаления старого — типичная утечка памяти и баг "обработчик срабатывает несколько раз".

```jsx
// Наглядно: что происходит при смене userId
useEffect(() => {
  console.log("Подписка на пользователя", userId);
  return () => console.log("Отписка от пользователя", userId);
}, [userId]);

// При смене userId с 1 на 2 в консоли будет:
// "Отписка от пользователя 1"   <- cleanup от старого эффекта
// "Подписка на пользователя 2"  <- новый эффект
```

## 4. Data fetching в useEffect — самый частый практический кейс

```jsx
function UserProfile({ userId }) {
  const [user, setUser] = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    let cancelled = false;
    setLoading(true);
    setError(null);

    fetch(`/api/users/${userId}`)
      .then(res => res.json())
      .then(data => { if (!cancelled) { setUser(data); setLoading(false); } })
      .catch(err => { if (!cancelled) { setError(err); setLoading(false); } });

    return () => { cancelled = true; }; // защита от race condition
  }, [userId]);

  if (loading) return <p>Загрузка...</p>;
  if (error) return <p>Ошибка: {error.message}</p>;
  return <p>{user.name}</p>;
}
```

**Зачем нужен `cancelled` флаг — это реальная проблема, не перестраховка.** Представь: пользователь быстро переключает `userId` с 1 на 2. Запрос за юзера 1 ещё не завершился, а уже стартовал запрос за юзера 2. Если запрос за юзера 1 завершится **позже** — он перезапишет state данными юзера 1, хотя на экране уже должен быть юзер 2. Это называется **race condition**. Флаг `cancelled`, выставляемый в cleanup, не даёт устаревшему запросу применить свой результат.

**На собесе это топовый вопрос**: "Как избежать race condition при фетче данных в useEffect?" — ответ именно про cancel-флаг (или `AbortController` — более современный способ, см. ниже).

```jsx
useEffect(() => {
  const controller = new AbortController();
  fetch(`/api/users/${userId}`, { signal: controller.signal })
    .then(res => res.json())
    .then(setUser)
    .catch(err => { if (err.name !== "AbortError") setError(err); });
  return () => controller.abort(); // реально прерывает сетевой запрос
}, [userId]);
```
`AbortController` — более правильный способ, потому что реально отменяет сетевой запрос, а не просто игнорирует его результат.

## 5. Бесконечный цикл ре-рендеров — вторая топовая ловушка

```jsx
function Bad() {
  const [data, setData] = useState({});

  useEffect(() => {
    setData({ loaded: true }); // создаёт НОВЫЙ объект каждый раз
  }, [data]); // data меняется -> эффект снова срабатывает -> снова меняет data -> бесконечно

  return <div>...</div>;
}
```
**Почему это ломается:** `{}` (новый объект) в зависимостях всегда "не равен" предыдущему через `Object.is`, даже если содержимое одинаковое — объекты сравниваются по ссылке, не по значению. Эффект меняет `data`, значит зависимость изменилась, значит эффект должен сработать снова — бесконечный цикл.

**Как чинить:** не класть в зависимости то, что сам эффект изменяет, либо использовать функциональное обновление (`setData(prev => ...)`), которое не требует `data` в зависимостях вообще, либо `useMemo`/примитивные значения вместо объектов там, где сравнение по ссылке — проблема.

## 6. useEffect vs useLayoutEffect — коротко, но по существу

`useEffect` — асинхронный относительно рендера, браузер может успеть отрисовать кадр **до** того, как эффект выполнится. Подходит для 95% случаев (фетч, подписки, логирование).

`useLayoutEffect` — выполняется **синхронно**, сразу после обновления DOM, но **до** того как браузер отрисует кадр на экране. Используй, только если нужно **измерить** DOM (например, высоту элемента) и **синхронно** поменять что-то, чтобы избежать визуального "мигания" (flicker).

```jsx
useLayoutEffect(() => {
  const height = ref.current.getBoundingClientRect().height;
  setTooltipPosition(height); // нужно применить ДО отрисовки, иначе будет видно "прыжок"
}, []);
```
**На собесе:** "Когда используешь useLayoutEffect вместо useEffect?" — ответ: почти никогда, только когда есть видимый визуальный артефакт (мигание/скачок) от асинхронного применения изменений после замера DOM.

## 7. Практика — реши сам, потом сверься с решением

### Задача 7.1 — найди баг
```jsx
function SearchBox() {
  const [query, setQuery] = useState("");
  const [results, setResults] = useState([]);

  useEffect(() => {
    fetch(`/api/search?q=${query}`).then(r => r.json()).then(setResults);
  });

  return <input value={query} onChange={e => setQuery(e.target.value)} />;
}
```
Что не так с этим кодом?

<details>
<summary>Ответ</summary>
Эффект без массива зависимостей — срабатывает после **каждого** рендера, включая рендеры, вызванные обновлением `results` из самого эффекта. Это создаёт лишние запросы и потенциальный цикл. Нужно указать `[query]`, чтобы эффект срабатывал только при изменении поискового запроса, а не при любом ре-рендере.

```jsx
useEffect(() => {
  fetch(`/api/search?q=${query}`).then(r => r.json()).then(setResults);
}, [query]);
```
Но и это ещё не идеально — без debounce каждая буква вызывает запрос. Правильная версия сочетает это с debounce (см. задачу 7.3).
</details>

### Задача 7.2 — исправь утечку
```jsx
function Clock() {
  const [time, setTime] = useState(new Date());

  useEffect(() => {
    setInterval(() => setTime(new Date()), 1000);
  }, []);

  return <p>{time.toLocaleTimeString()}</p>;
}
```
Что произойдёт, если этот компонент размонтируется?

<details>
<summary>Ответ</summary>
`setInterval` продолжит работать даже после размонтирования компонента — попытка вызвать `setTime` на размонтированном компоненте (утечка памяти + предупреждение в консоли в старых версиях React). Нужен cleanup:

```jsx
useEffect(() => {
  const id = setInterval(() => setTime(new Date()), 1000);
  return () => clearInterval(id);
}, []);
```
</details>

### Задача 7.3 — напиши поиск с debounce и защитой от race condition
Условие: при вводе в поле поиска запрос должен отправляться не чаще раза в 400мс после паузы, и устаревший ответ не должен перезаписывать актуальный результат.

<details>
<summary>Решение</summary>
```jsx
function SearchBox() {
  const [query, setQuery] = useState("");
  const [results, setResults] = useState([]);

  useEffect(() => {
    if (!query) { setResults([]); return; }

    const timer = setTimeout(() => {
      const controller = new AbortController();
      fetch(`/api/search?q=${query}`, { signal: controller.signal })
        .then(r => r.json())
        .then(setResults)
        .catch(err => { if (err.name !== "AbortError") console.error(err); });

      // cleanup ловит и таймер, и контроллер через замыкание
      return () => controller.abort();
    }, 400);

    return () => clearTimeout(timer);
  }, [query]);

  return <input value={query} onChange={e => setQuery(e.target.value)} />;
}
```
Обрати внимание: здесь cleanup из `setTimeout` (clearTimeout) отменяет ещё не выполнившийся запрос, а AbortController отменяет уже улетевший запрос — это два разных момента защиты.
</details>

### Задача 7.4 — вынеси повторяющуюся логику в custom hook
Условие: у тебя в трёх компонентах повторяется один и тот же паттерн подписки на `window.resize`. Вынеси в хук `useWindowWidth()`.

<details>
<summary>Решение</summary>
```jsx
function useWindowWidth() {
  const [width, setWidth] = useState(window.innerWidth);

  useEffect(() => {
    const handler = () => setWidth(window.innerWidth);
    window.addEventListener("resize", handler);
    return () => window.removeEventListener("resize", handler);
  }, []);

  return width;
}

// Использование:
function Component() {
  const width = useWindowWidth();
  return <p>Ширина окна: {width}px</p>;
}
```
Это частый вопрос-задание: "покажи, как ты рефакторишь повторяющийся useEffect в custom hook" — показывает, что ты не просто знаешь синтаксис, а понимаешь идею переиспользования логики через хуки.
</details>

## 8. Как отвечать, если спросят "объясни useEffect" одним связным ответом

Хорошая структура ответа вслух (не зазубренная, а по смыслу):
> "useEffect — способ выполнить побочный эффект после рендера: запрос к серверу, подписку, работу с DOM API напрямую. Массив зависимостей определяет, когда эффект перезапускается — React сравнивает значения между рендерами. Если эффект что-то 'включает' — нужно возвращать cleanup-функцию, которая это выключит перед следующим запуском или при размонтировании. Самые частые баги — забытая зависимость (stale closure) и отсутствие cleanup при подписках/таймерах, что приводит к утечкам и race condition при фетче данных."

Такой ответ за 30-40 секунд закрывает 80% того, что интервьюер хочет услышать, и дальше он будет уточнять детали — а у тебя уже есть конкретные примеры выше под каждую деталь.
