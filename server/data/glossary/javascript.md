# ООП — чтобы реально понять, а не просто запомнить термины

Все примеры на Python, раз это твой основной стек.

---

## 1. Зачем вообще ООП

Просто: это способ организовать код так, чтобы данные и поведение над ними жили вместе, а не разбросаны по функциям. Вместо "функция обрабатывает словарь пользователя" — "объект User знает, как сам себя обработать". Это упрощает разделение ответственности и переиспользование кода в большом проекте.

---

## 2. Четыре столпа ООП — с примерами, а не просто определениями

### Инкапсуляция
Прячем внутреннее устройство объекта, оставляем снаружи только нужный интерфейс.

```python
class BankAccount:
    def __init__(self, balance):
        self._balance = balance  # "приватное" по конвенции (один _)

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("Сумма должна быть положительной")
        self._balance += amount

    def get_balance(self):
        return self._balance
```
Смысл: снаружи никто не может напрямую поставить `balance = -100`, минуя проверку. В Python нет настоящей приватности как в Java — `_balance` (одно подчёркивание) — это соглашение "не трогай снаружи", `__balance` (два подчёркивания) — включает name mangling (реально усложняет доступ извне, но не делает недоступным).

**На собесе спросят:** "Как в Python реализована приватность?" — ответ именно такой: через конвенции, а не через жёсткий контроль языка, как в Java/C#.

### Наследование
Один класс берёт поведение другого и расширяет/переопределяет его.

```python
class Animal:
    def __init__(self, name):
        self.name = name

    def speak(self):
        return f"{self.name} издаёт звук"

class Dog(Animal):
    def speak(self):  # переопределение метода
        return f"{self.name} говорит Гав!"
```
Смысл: не переписывать общую логику (`__init__`, общие методы) в каждом классе.

**Важный нюанс, который часто спрашивают:** наследование — это связь "является" (Dog **is an** Animal). Если связь скорее "содержит" — нужна композиция, не наследование (см. пункт 5).

### Полиморфизм
Разные классы отвечают на один и тот же вызов по-своему.

```python
animals = [Dog("Рекс"), Cat("Мурка")]
for a in animals:
    print(a.speak())  # у каждого своя реализация speak()
```
Код, который вызывает `a.speak()`, не знает и не должен знать, с каким конкретно классом работает — это и есть полиморфизм. Практическая польза: можно добавить новый класс `Cow`, и весь остальной код не меняется.

### Абстракция
Выделяем общий интерфейс, скрывая детали реализации.

```python
from abc import ABC, abstractmethod

class PaymentProvider(ABC):
    @abstractmethod
    def pay(self, amount):
        ...

class StripeProvider(PaymentProvider):
    def pay(self, amount):
        print(f"Оплата {amount} через Stripe")
```
`ABC` не даст создать экземпляр `PaymentProvider` напрямую и заставит все подклассы реализовать `pay`. Смысл — зафиксировать контракт: "любой платёжный провайдер обязан иметь метод pay", а как именно — его личное дело.

## 3. Composition over inheritance — важный современный принцип

Наследование жёстко связывает классы навсегда (изменил родителя — сломал всех детей). Композиция — гибче: класс не наследует, а **содержит** другой объект и делегирует ему работу.

```python
# Наследование (жёстко, "is a")
class ElectricCar(Car):
    ...

# Композиция (гибко, "has a")
class Car:
    def __init__(self, engine):
        self.engine = engine  # можно подставить любой Engine

    def start(self):
        return self.engine.start()
```
На собесе это частый вопрос: "Когда выбрать композицию вместо наследования?" — ответ: когда связь не "является", а "содержит/использует", или когда нужна гибкость подставлять разное поведение в рантайме, или когда иерархия наследования грозит стать глубокой и хрупкой.

## 4. classmethod / staticmethod / property — путают почти все

```python
class Pizza:
    def __init__(self, size):
        self.size = size

    @classmethod
    def margherita(cls):          # альтернативный конструктор
        return cls(size="medium")

    @staticmethod
    def is_valid_size(size):      # просто утилита, не трогает self/cls
        return size in ("small", "medium", "large")

    @property
    def description(self):        # выглядит как атрибут, а не метод
        return f"Pizza размера {self.size}"
```
- `@classmethod` — первый аргумент `cls`, часто используют как альтернативные конструкторы (`Pizza.margherita()` вместо `Pizza("medium")`).
- `@staticmethod` — не получает ни `self`, ни `cls` — просто функция, логически связанная с классом.
- `@property` — метод, который вызывается без скобок, как атрибут (`pizza.description`, а не `pizza.description()`).

## 5. Магические методы (dunder methods) — Python-специфика, любят спрашивать

```python
class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __repr__(self):           # для разработчика (в консоли, логах)
        return f"Point({self.x}, {self.y})"

    def __eq__(self, other):      # логика сравнения ==
        return self.x == other.x and self.y == other.y

    def __add__(self, other):     # логика оператора +
        return Point(self.x + other.x, self.y + other.y)
```
Без `__eq__` два разных объекта с одинаковыми x/y будут считаться неравными (по умолчанию сравнивается identity, как `is`). Без `__repr__` при печати объекта увидишь что-то вроде `<Point object at 0x7f...>` вместо человеческого представления.

## 6. Множественное наследование и MRO — если спросят про Python отдельно от Java/C#

Python поддерживает множественное наследование (в отличие от Java/C#, где только интерфейсы). Порядок разрешения методов (**MRO — Method Resolution Order**) определяется по алгоритму C3 linearization — по сути, "слева-направо, снизу-вверх, без повторов". Посмотреть можно через `ClassName.__mro__`.

```python
class A:
    def hello(self): return "A"

class B(A):
    def hello(self): return "B"

class C(A):
    def hello(self): return "C"

class D(B, C):
    pass

D().hello()  # "B" — ищет сначала в B (по MRO), не в A
```
Не обязательно помнить алгоритм C3 наизусть — важно понимать: порядок родителей в объявлении класса имеет значение.

## 7. SOLID — раз уровня Middle, скорее всего спросят хотя бы пару принципов

- **S — Single Responsibility.** Один класс — одна причина для изменения. Не смешивай в одном классе бизнес-логику и, например, отправку email.
- **O — Open/Closed.** Класс должен быть открыт для расширения, но закрыт для изменения — новую функциональность добавляешь через наследование/композицию, не переписывая существующий рабочий код.
- **L — Liskov Substitution.** Подкласс должен быть заменяем на место родителя без поломки логики. Классический антипример: `Square extends Rectangle`, где изменение width у Rectangle должно менять и height у Square — ломает ожидания кода, который работает с Rectangle.
- **I — Interface Segregation.** Лучше несколько маленьких специфичных интерфейсов, чем один большой "на все случаи" — не заставляй класс реализовывать методы, которые ему не нужны.
- **D — Dependency Inversion.** Зависеть от абстракций, а не от конкретных реализаций (см. пример с `PaymentProvider` выше — код работает с абстрактным интерфейсом, а не жёстко со Stripe).

**Как отвечать, если попросят "объясни SOLID":** не пересказывай все 5 по памяти скороговоркой — выбери 2, которые понимаешь глубже всего, и объясни на примере из своего кода. Это выглядит убедительнее, чем зазубренный список.
